# Testing and Quality Skill

## Назначение

Этот skill используется для задач, связанных с тестированием и проверкой качества локальной RAG-платформы LOCAL-RAG-PLATFORM.

Главная цель:

- после изменений быстро понять, что импорт, поиск, источники и ответы не сломались.

## Что обязательно проверять после изменений

После любых изменений в RAG, импорте, поиске, Qdrant, PostgreSQL, Ollama или UI нужно проверить:

1. Проект запускается.
2. /health отвечает.
3. /ui/jobs открывается.
4. /ui/ingest открывается.
5. /ui/consult открывается.
6. /ui/pages-search открывается.
7. Можно импортировать тестовый документ.
8. Создаются chunks.
9. Создаются embeddings.
10. Данные попадают в Qdrant.
11. Поиск находит релевантный источник.
12. Ответ содержит источники.
13. Если источников нет, работает fallback-empty.

## Минимальный smoke-test

Минимальная проверка после изменения:

1. Запустить проект:

```powershell
scripts/start.ps1
```

2. Проверить:

```text
http://localhost:8787/health
```

3. Открыть:

```text
http://localhost:8787/ui/consult
```

4. Задать вопрос по уже импортированному документу.

5. Проверить:

* есть ответ;
* есть источники;
* ответ не выдуман;
* источники соответствуют вопросу.

## Smoke-test импорта

Для проверки импорта использовать небольшой тестовый файл, а не тяжёлый PDF.

Проверить:

* файл принимается;
* задача появляется в /ui/jobs;
* status становится completed;
* chunks создаются;
* документ появляется в поиске;
* вопрос по документу возвращает источник.

## Smoke-test поиска

Проверить минимум 3 типа запросов:

1. Общий смысловой вопрос.
2. Запрос с точным тегом/сигналом.
3. Запрос, по которому в базе нет ответа.

Ожидаемое поведение:

* смысловой вопрос находит релевантные источники;
* точный тег/сигнал находится lexical или hybrid search;
* если ответа нет, система возвращает честный fallback-empty.

## Проверка PDF-страниц

Если изменение связано с PDF, проверить:

* page_number;
* page_type;
* поиск по PDF-страницам;
* фильтр по типу страницы;
* отображение источника с номером страницы.

Типы страниц:

* title
* contents
* changelog
* legal
* signals
* table
* scheme
* screen
* text

## Проверка качества ответа

Хороший ответ должен:

* быть на русском языке;
* ссылаться на найденные источники;
* не выдумывать факты;
* сохранять оригинальные технические обозначения;
* быть полезным инженеру АСУ ТП;
* явно говорить, если данных недостаточно.

Плохой ответ:

* без источников;
* слишком общий;
* придумывает данные;
* игнорирует выбранный документ;
* игнорирует фильтры;
* переводит или искажает технические теги.

## Регрессии, которых нельзя допускать

После изменений нельзя сломать:

* импорт data/raw;
* поддержку txt, md, pdf, docx, csv, xlsx, xls;
* фоновый импорт;
* защиту от дублей;
* progress jobs;
* semantic search;
* lexical search;
* фильтры UI;
* fallback-empty;
* русские тексты интерфейса.

## Ограничения слабого ноутбука

Тесты не должны перегружать ноутбук:

* не использовать большой PDF для каждого теста;
* не запускать массовую переиндексацию без причины;
* не скачивать тяжёлые модели;
* не увеличивать topK без необходимости;
* не создавать большие временные файлы.

## Правила для Codex

* После изменения всегда предложить конкретный способ проверки.
* Если тесты не запускались, честно написать, что они не запускались.
* Не заявлять, что всё проверено, если проверка не выполнялась.
* Если запуск тестов невозможен, объяснить почему и дать ручную проверку.
* Для ошибок сначала воспроизвести проблему, потом исправлять.
* После исправления показать:

  * что было причиной;
  * что изменено;
  * как проверить;
  * какие риски остались.
