# Vector Search Skill

## Назначение

Этот skill используется для задач, связанных с поиском по документам в локальной RAG-платформе.

Проект использует:

- Qdrant для векторного поиска;
- PostgreSQL для метаданных, документов, chunk-ов, статусов и журналов;
- embedding-модель qwen3-embedding:0.6b;
- semantic + lexical search;
- ответы по найденным источникам.

## Главная цепочка поиска

При изменениях в поиске всегда проверять цепочку:

1. Пользователь задаёт вопрос.
2. Система формирует search query.
3. Выполняется semantic search по Qdrant.
4. Выполняется lexical search по тексту/метаданным, если предусмотрено.
5. Применяются фильтры:
   - документ;
   - тип PDF-страницы;
   - инженерная тема;
   - тег;
   - сигнал.
6. Результаты объединяются и ранжируются.
7. Отбираются источники для ответа.
8. Модель отвечает только по найденным источникам.
9. Пользователь видит ответ и источники.

## Обязательные правила retrieval

- Не отвечать без источников.
- Если релевантных источников нет, использовать честный fallback-empty.
- Не выдумывать факты по документам.
- Не смешивать результаты разных документов, если пользователь выбрал конкретный документ.
- Не игнорировать фильтры UI.
- Для инженерных вопросов отдавать приоритет точным совпадениям сигналов, тегов, названий блоков, оборудования и обозначений.

## Qdrant

При работе с Qdrant учитывать:

- векторы должны соответствовать embedding-модели qwen3-embedding:0.6b;
- payload должен сохранять полезные metadata;
- при переиндексации документа старые vectors/chunks не должны давать дубли в поиске;
- при удалении документа связанные vectors должны удаляться или становиться недоступными;
- нельзя без причины пересоздавать коллекцию Qdrant;
- нельзя ломать уже проиндексированные документы.

## PostgreSQL metadata

Для поиска и ответа важны metadata:

- document_id
- filename
- chunk_index
- page_number
- page_type
- section_title, если есть
- tags, если есть
- signals, если есть
- engineering_topic, если есть
- source text или ссылка на chunk/page

Если меняется структура metadata, нужно проверить импорт, поиск и отображение источников.

## Semantic + lexical search

Semantic search хорошо ищет по смыслу.

Lexical search важен для АСУ ТП, потому что в документах часто есть точные обозначения:

- теги;
- сигналы;
- клеммы;
- имена блоков;
- номера модулей;
- названия оборудования;
- обозначения шкафов;
- имена параметров.

Поэтому при вопросах с точными кодами и тегами нельзя полагаться только на semantic search.

## Русскоязычные ответы

Все пользовательские сообщения, ошибки и подсказки UI писать на русском языке.

## Ограничения слабого ноутбука

Проект работает локально на слабом ноутбуке:

- не добавлять тяжёлые rerank-модели без отдельного разрешения;
- не делать лишних повторных embeddings;
- не запускать массовую переиндексацию без необходимости;
- не увеличивать topK слишком сильно без причины;
- учитывать ограниченное место на диске C:.

## Проверка после изменений

После любых изменений в поиске нужно проверить:

1. /ui/consult
2. поиск по всем источникам;
3. поиск по конкретному документу;
4. поиск по типу PDF-страницы;
5. вопрос с точным тегом или сигналом;
6. ситуацию, когда источников нет;
7. отображение источников в ответе.

## Правила для Codex

- Перед изменением поиска найти существующие файлы, отвечающие за search/retrieval/Qdrant/embeddings.
- Сначала объяснить план.
- Не переписывать весь retrieval без подтверждения.
- Делать изменения маленькими шагами.
- После изменения написать:
  - какие файлы изменены;
  - что изменилось;
  - как проверить результат.
- Если задача может повлиять на импорт, обязательно указать это отдельно.
