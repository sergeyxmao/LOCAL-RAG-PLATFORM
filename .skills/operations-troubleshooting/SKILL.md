# Operations and Troubleshooting Skill

## Назначение

Этот skill используется для задач, связанных с запуском, эксплуатацией и диагностикой локальной RAG-платформы LOCAL-RAG-PLATFORM.

Проект работает локально на:

- Windows;
- Docker Desktop;
- WSL2;
- PostgreSQL;
- Qdrant;
- Open WebUI;
- Ollama;
- kb-api.

## Нормальный запуск

Стандартный запуск проекта:

1. Проверить, что Docker Desktop запущен.
2. Проверить, что WSL2 работает.
3. Запустить проект:

```powershell
scripts/start.ps1
```

4. Проверить kb-api:

```text
http://localhost:8787/health
```

5. Проверить основные UI:

```text
http://localhost:8787/ui/jobs
http://localhost:8787/ui/ingest
http://localhost:8787/ui/consult
http://localhost:8787/ui/pages-search
```

6. Проверить Open WebUI:

```text
http://localhost:3000
```

## Основные сервисы

При диагностике учитывать:

* kb-api отвечает на порту 8787;
* Open WebUI отвечает на порту 3000;
* PostgreSQL хранит документы, chunks, jobs, metadata;
* Qdrant хранит vectors;
* Ollama даёт локальные модели;
* ingestion-worker пока каркас, основная логика сейчас в kb-api.

## Проверка после запуска

После запуска проверить:

* /health возвращает нормальный статус;
* /ui/jobs открывается;
* /ui/ingest открывается;
* /ui/consult открывается;
* /ui/pages-search открывается;
* контейнеры Docker запущены;
* нет ошибок подключения к PostgreSQL;
* нет ошибок подключения к Qdrant;
* Ollama доступен;
* нужные модели существуют:

  * qwen3:4b;
  * qwen3-embedding:0.6b.

## Диагностика Docker и WSL2

Если проект не запускается, сначала проверить:

* запущен ли Docker Desktop;
* работает ли WSL2;
* есть ли состояние Running у docker-desktop;
* нет ли конфликта портов;
* хватает ли места на диске C:;
* не сломались ли volume Docker.

Не предлагать переустановку Docker как первый шаг.
Сначала делать мягкую диагностику.

## Диагностика импорта

Если импорт завис или упал, проверить:

1. /ui/jobs
2. статус job;
3. progress_message;
4. error;
5. место на диске;
6. состояние Qdrant;
7. состояние PostgreSQL;
8. не импортируется ли уже такой же файл;
9. включён ли createVisualAssets для тяжёлого PDF.

Для больших PDF рекомендовать:

* фоновый импорт;
* createVisualAssets=false;
* сначала текстовый проход;
* потом точечно переиндексировать нужные PDF с preview.

## Проблемы с диском

Уже была реальная проблема:

No space left on device: WAL buffer size exceeds available disk space

Это связано с нехваткой места для Qdrant/WAL.

При такой ошибке:

* не винить сразу модель;
* проверить свободное место на C:;
* проверить Docker volumes;
* проверить временные файлы;
* проверить дубли индексации;
* рекомендовать очистку безопасных кэшей;
* не удалять volumes с данными без подтверждения пользователя.

## Правила безопасной диагностики

Codex не должен предлагать разрушительные команды без предупреждения.

Опасные действия:

* удаление Docker volumes;
* очистка всей базы;
* пересоздание Qdrant collection;
* удаление data/raw;
* удаление PostgreSQL data;
* массовая переиндексация всех документов;
* сброс Docker Desktop.

Перед такими действиями нужен отдельный план и подтверждение.

## Логи

При диагностике можно смотреть:

* логи kb-api;
* логи Docker containers;
* ошибки PostgreSQL;
* ошибки Qdrant;
* ошибки Ollama;
* статусы jobs.

Но нельзя выводить полный текст документов или chunks в логи.

## Проверка поиска

Если пользователь жалуется, что ответы плохие:

1. Проверить, импортирован ли документ.
2. Проверить, есть ли chunks.
3. Проверить, есть ли vectors в Qdrant.
4. Проверить semantic search.
5. Проверить lexical search.
6. Проверить фильтры UI.
7. Проверить, показываются ли источники.
8. Проверить fallback-empty.

## Проверка после исправлений

После любой операции по диагностике или исправлению нужно написать:

* что проверено;
* что найдено;
* какие файлы изменены, если менялись;
* какие команды запускались;
* как пользователю проверить результат в браузере.

## Правила для Codex

* Сначала диагностировать, потом менять.
* Не делать массовые очистки без подтверждения.
* Не удалять данные пользователя без подтверждения.
* Не менять стек проекта.
* Не скачивать тяжёлые модели без разрешения.
* Сохранять русские пользовательские тексты.
* Все инструкции для пользователя давать пошагово.
* Если задача связана с ошибкой, сначала найти первопричину, а не лечить симптом.
