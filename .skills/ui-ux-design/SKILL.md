# UI/UX Design Skill

## Назначение

Этот skill используется для задач, связанных с интерфейсом LOCAL-RAG-PLATFORM.

Главная цель интерфейса:

- сделать локальную RAG-платформу удобным рабочим инструментом инженера АСУ ТП;
- быстро импортировать документы;
- быстро искать по базе;
- понятно видеть источники;
- не путаться в статусах задач;
- не перегружать слабый ноутбук тяжёлыми UI-эффектами.

## Общий стиль

Интерфейс должен быть:

- спокойным;
- техническим;
- аккуратным;
- современным;
- без лишней декоративности;
- удобным для долгой работы;
- на русском языке.

Визуальный стиль:

- светлый интерфейс по умолчанию;
- хороший контраст текста;
- понятные кнопки;
- аккуратные карточки;
- достаточно свободного пространства;
- единые отступы;
- единые состояния кнопок;
- читаемые таблицы;
- минимум визуального шума.

## Главные страницы

В проекте есть ключевые страницы:

- /ui/consult — консультация и ответы по документам;
- /ui/ingest — импорт документов;
- /ui/jobs — задачи импорта и статусы;
- /ui/pages-search — поиск по PDF-страницам.

При изменениях UI не ломать эти страницы и их назначение.

## /ui/consult

Страница консультации должна помогать быстро получить ответ по документам.

Важные элементы:

- поле вопроса;
- выбор источников;
- режим поиска:
  - все источники;
  - только текст;
  - только PDF-страницы;
- фильтры по документу, page_type, тегу, сигналу, теме;
- область ответа;
- список источников;
- честное сообщение, если источников нет.

Хороший UX:

- пользователь сразу понимает, где задать вопрос;
- видно, по каким источникам идёт поиск;
- источники ответа заметны и читаемы;
- если ответ плохой, можно быстро понять, какие источники были использованы;
- fallback-empty не выглядит как ошибка приложения.

## /ui/ingest

Страница импорта должна быть простой.

Важные элементы:

- выбор файла или папки;
- понятный режим импорта;
- переключатель createVisualAssets;
- предупреждение для тяжёлых PDF;
- кнопка запуска импорта;
- ссылка на /ui/jobs для контроля прогресса.

Для слабого ноутбука:

- по умолчанию не навязывать тяжёлый импорт;
- для больших PDF явно рекомендовать фоновый режим;
- createVisualAssets=false должен быть понятен пользователю.

## /ui/jobs

Страница задач должна показывать состояние импорта без путаницы.

Важные элементы:

- статус;
- прогресс;
- имя документа;
- processed_items / total_items;
- progress_message;
- ошибка, если есть;
- кнопки:
  - остановить;
  - повторить;
- время начала/завершения, если доступно.

Статусы должны быть визуально различимы:

- ожидает;
- выполняется;
- завершено;
- ошибка;
- остановлено.

Ошибки писать понятным русским языком.

## /ui/pages-search

Страница поиска по PDF-страницам должна помогать работать с технической документацией.

Важные элементы:

- строка поиска;
- фильтр по документу;
- фильтр по page_type;
- номер страницы;
- тип страницы;
- краткий фрагмент текста;
- ссылка/переход к источнику, если реализовано.

Для АСУ ТП особенно важны:

- signals;
- table;
- scheme;
- screen;
- text;
- contents.

## Источники ответа

Источники — ключевой элемент доверия.

Источник должен показывать:

- имя документа;
- номер страницы, если есть;
- page_type, если есть;
- фрагмент текста;
- почему источник выбран, если это реализовано;
- совпавший тег/сигнал, если есть.

Нельзя прятать источники в малозаметный блок.

## Пустые состояния

Пустое состояние должно объяснять, что делать дальше.

Примеры:

- документы ещё не импортированы;
- поиск ничего не нашёл;
- источники не найдены;
- jobs пока нет;
- PDF-страницы ещё не созданы;
- Qdrant недоступен;
- Ollama недоступен.

Плохой UX:

- просто пустой экран;
- непонятная ошибка;
- английский технический текст для пользователя;
- сообщение без следующего шага.

## Ошибки

Ошибки должны быть:

- на русском языке;
- короткие;
- понятные;
- без лишних внутренних деталей;
- с подсказкой, что проверить.

Пример хорошей ошибки:

Не удалось импортировать документ. Проверьте свободное место на диске и откройте страницу задач.

Пример плохой ошибки:

Unhandled exception in worker undefined stack trace...

## Состояния загрузки

Для долгих операций показывать:

- что сейчас происходит;
- какой документ обрабатывается;
- сколько уже обработано;
- что это может занять время;
- где смотреть прогресс.

Не блокировать интерфейс без объяснения.

## Дизайн для слабого ноутбука

Не использовать без необходимости:

- тяжёлые анимации;
- большие превью всех страниц сразу;
- бесконечные списки без ограничения;
- автообновление слишком часто;
- тяжёлые графики;
- массовую отрисовку PDF preview.

Предпочитать:

- простую верстку;
- таблицы с ограничением;
- пагинацию;
- ручное обновление или мягкий polling;
- ленивую загрузку preview;
- компактные карточки.

## Русские тексты

Все пользовательские тексты должны быть на русском языке:

- кнопки;
- заголовки;
- подсказки;
- ошибки;
- пустые состояния;
- статусы;
- предупреждения.

Технические термины можно оставлять, если они привычны:

- chunk;
- embedding;
- Qdrant;
- Ollama;
- PDF;
- page_type;
- fallback-empty.

## Правила для Codex

- Перед изменением UI найти текущие frontend files, связанные со страницей.
- Сначала предложить план интерфейса.
- Не менять весь дизайн приложения без подтверждения.
- Делать улучшения маленькими шагами.
- Не ломать текущие маршруты:
  - /ui/consult
  - /ui/ingest
  - /ui/jobs
  - /ui/pages-search
- После изменения написать:
  - какие файлы изменены;
  - что улучшено;
  - как проверить в браузере;
  - какие UX-проблемы ещё остались.
- Если изменение UI влияет на backend API, указать это отдельно.
