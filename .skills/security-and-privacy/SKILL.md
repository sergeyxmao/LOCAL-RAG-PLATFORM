# Security and Privacy Skill

## Назначение

Этот skill используется для задач, связанных с безопасностью и приватностью локальной RAG-платформы LOCAL-RAG-PLATFORM.

Проект предназначен для работы с рабочими документами АСУ ТП и должен работать локально.

Главное правило:

- документы пользователя не должны уходить во внешние облачные сервисы без явного разрешения.

## Базовые принципы

- Всё работает локально.
- Документы пользователя считаются приватными.
- Логи не должны содержать полный текст документов.
- Секреты, токены и пароли нельзя хранить в коде.
- Нельзя отправлять содержимое документов во внешние API без отдельного разрешения.
- Нельзя добавлять телеметрию или внешние сервисы без подтверждения.
- Нельзя ломать текущий локальный режим работы.

## Документы пользователя

При работе с документами учитывать:

- исходные файлы лежат в data/raw;
- импортированные документы попадают в PostgreSQL и Qdrant;
- в chunks могут быть рабочие данные, сигналы, теги, схемы, оборудование;
- эти данные нельзя выводить в debug-логи целиком;
- нельзя делать автопубликацию или внешнюю синхронизацию документов.

## Логи

В логах допустимо хранить:

- document_id;
- filename;
- job_id;
- status;
- количество chunk-ов;
- количество страниц;
- тип ошибки;
- время выполнения.

В логах нежелательно хранить:

- полный текст chunk-ов;
- большие фрагменты документов;
- ключи API;
- токены;
- пароли;
- приватные пути пользователя, если они не нужны для диагностики.

## Внешние API

По умолчанию запрещено:

- отправлять документы во внешние LLM API;
- отправлять chunks во внешние embedding API;
- добавлять облачный OCR;
- добавлять облачную телеметрию;
- отправлять аналитику использования наружу.

Если внешний API действительно нужен, Codex должен сначала предложить план и явно указать:

- какие данные будут отправляться;
- зачем это нужно;
- можно ли сделать локально;
- как отключить внешний режим;
- какие риски для приватности.

## Ollama и локальные модели

Разрешённый локальный режим:

- Ollama;
- qwen3:4b;
- qwen3-embedding:0.6b;
- Open WebUI;
- локальный kb-api.

Нельзя без разрешения менять локальный режим на облачный.

## Файлы конфигурации и секреты

При работе с конфигами:

- не коммитить .env с реальными секретами;
- использовать .env.example для примеров;
- не писать токены в README, AGENTS.md или docs;
- не вставлять реальные пароли в тесты;
- не выводить секреты в ошибках.

## Доступ к данным

Если в будущем появятся несколько пользователей, обязательно учитывать:

- документ должен принадлежать конкретному пользователю;
- поиск должен фильтроваться по user_id;
- пользователь не должен видеть чужие документы;
- административные функции должны быть отделены от пользовательских.

Даже если сейчас проект локальный и однопользовательский, новые изменения не должны мешать будущей изоляции пользователей.

## Удаление и переиндексация

При удалении документа нужно учитывать:

- удалить или отключить документ в PostgreSQL;
- удалить связанные chunks;
- удалить или отключить vectors в Qdrant;
- не оставлять старые данные доступными для поиска;
- не создавать дубли при повторном импорте.

## Ошибки безопасности

Сообщения пользователю должны быть понятными, но не раскрывать лишнее.

Например:

Правильно:
- Не удалось импортировать документ. Проверьте файл и место на диске.

Неправильно:
- Ошибка с полным внутренним путём, токеном, SQL-запросом или содержимым chunk-а.

## Правила для Codex

- Перед изменением security-sensitive кода найти связанные routes/services/config/env/logging файлы.
- Сначала объяснить план.
- Не добавлять внешние сервисы без подтверждения.
- Не ослаблять локальную приватность.
- Не логировать полный текст документов.
- Не удалять проверки безопасности без объяснения причины.
- После изменения написать:
  - какие файлы изменены;
  - что изменилось;
  - какие риски закрыты;
  - как проверить.
