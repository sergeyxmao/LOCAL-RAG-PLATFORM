# Память инженера — Этап 3: LLM-извлечение случаев из документов (с очередью ревью)

## Что делает

«Память инженера» (Этап 1) наполнялась только вручную — через форму
«📝 Записать случай» на `/ui/v2/graph`. Реальные источники случаев —
вахтовые журналы, акты, отчёты — содержат десятки случаев в прозе,
переносить которые руками непосильно.

Этап 3 добавляет **ручное LLM-извлечение случаев** из текстовых
документов. На текстовом документе (`docx` / `txt` / `md`) в разделе
«База знаний → Документы» появляется кнопка **«Извлечь знания»**. По клику
облачный LLM читает текст документа и извлекает случаи вида
**оборудование / что произошло / что сделали**.

Ключевой принцип — **граф остаётся стерильным**: извлечённое НЕ попадает
в граф напрямую. Оно складывается в отдельную таблицу-очередь кандидатов
(`graph_extraction_candidates`) со статусом `pending`. На экране ревью
(«Граф знаний → Кандидаты») пользователь видит кандидатов,
сгруппированных по запуску извлечения, и **подтверждает / правит /
отклоняет** каждый случай. Только подтверждённый случай переносится в граф
как обычная запись случая (через тот же `recordCase` / `recordCaseTx`,
что и ручная форма, но с `author='agent:llm-extraction'`). Ни один
непроверенный узел в граф не попадает.

Извлечение запускается **только вручную** и **не затрагивает** импорт,
RAG-индексацию, парсер графа XLSX и рабочие коллекции Qdrant.

## Расположение в коде

  текста документа (склейка чанков), сегментация крупных документов,

## Контракт ответа модели

Модель обязана вернуть СТРОГО один JSON-объект — массив случаев:

```json
{
  "cases": [
    {
      "equipment": { "name": "...", "model": "...", "location": "..." },
      "fault": { "text": "...", "date": "YYYY-MM-DD" },
      "solution": { "text": "...", "date": "YYYY-MM-DD" },
      "object": "...",
      "confidence": 0.0,
      "source_quote": "..."
    }
  ]
}
```

- Обязательны только `equipment.name` и `fault.text` — случай без них
  отбрасывается на нормализации.
- Остальные поля опциональны / `null`.
- `source_quote` — короткий фрагмент-обоснование из текста (для проверки
  человеком на экране ревью).
- `confidence` — оценка уверенности модели (0..1); при отсутствии — `0.5`.
- Даты — `YYYY-MM-DD`, только если однозначно определяются из текста.
- JSON-ремонт ответа выполняется тем же паттерном, что и в
  `contextualEnrichmentService` (снятие code-fence, выдёргивание первого
  `{...}`, авто-починка хвостовых запятых и незакрытых скобок).
- Дубли внутри одного запуска (совпадение `equipment.name` + `fault.text`
  без учёта регистра) схлопываются.
- При неудачном разборе JSON в лог `kb-api` пишется усечённый сырой ответ
  модели — `rawHead` (≤800 символов) и `rawLength` (полная длина ответа) —
  рядом со строкой `"не удалось разобрать JSON ответа"`. Это постоянный
  инструмент отладки при смене моделей: если `rawHead` оборван на середине
  строки, ответ обрезан по лимиту токенов или reasoning'ом. Ключи и секреты
  в лог не попадают.

Случаи нормализуются в канонический `case_payload` (та же вложенная
структура) и пишутся в очередь кандидатов.

## Таблица очереди кандидатов

`graph_extraction_candidates` (создаётся в `ensureGraphSchema`,
идемпотентный DDL — `CREATE TABLE IF NOT EXISTS` + индексы):

| Колонка | Тип | Описание |
|---|---|---|
| `id` | UUID PK | `gen_random_uuid()` |
| `source_document_id` | UUID, FK → `documents(id)` `ON DELETE CASCADE` | документ-источник |
| `extraction_job_id` | UUID NOT NULL | группировка одного запуска извлечения |
| `case_payload` | JSONB | весь случай (equipment/fault/solution/object/source_quote/confidence) |
| `confidence` | REAL, nullable | уверенность (дублируется отдельной колонкой для сортировки/фильтров) |
| `status` | TEXT, дефолт `pending` | `pending` / `approved` / `rejected` |
| `created_at` | TIMESTAMPTZ, дефолт `now()` | момент извлечения |
| `reviewed_at` | TIMESTAMPTZ, nullable | момент подтверждения/отклонения |

Индексы: `idx_graph_extraction_candidates_document` (по
`source_document_id`), `idx_graph_extraction_candidates_status` (по
`status`), `idx_graph_extraction_candidates_job` (по `extraction_job_id`).

Извлечённые случаи пишутся сюда со `status='pending'`. В
`graph_nodes`/`graph_edges` на этапе извлечения **не пишется ничего**.

## Поток: извлечение → очередь → ревью → перенос в граф

1. **Извлечение.** UI POST `…/extract/:documentId`. Сервис синхронно
   проверяет gate (включено / провайдер / модель / промпт) и тип
   документа — при проблеме сразу отвечает `ok:false` с понятным русским
   сообщением (ничего не создаётся). Если всё ок — регистрирует
   `extraction_job_id`, запускает разбор LLM **в фоне** и сразу возвращает
   `{ ok:true, jobId, status:"running" }`.
2. **Опрос статуса.** UI опрашивает `…/extract/status/:jobId`. Статусы:
   `running` → `done` (случаи найдены и записаны) / `empty` (случаев нет)
   / `error` (модель/провайдер не ответили — ничего не создано).
3. **Очередь.** Найденные случаи лежат в `graph_extraction_candidates`
   со `status='pending'`. Граф не затронут.
4. **Ревью.** На `/ui/v2/graph/candidates`: слева — список запусков по
   документам (с разбивкой `на ревью / в графе / отклонён`); справа —
   карточки случаев целиком (оборудование + неисправность + решение +
   объект + цитата-обоснование + confidence).
5. **Подтверждение.** Кнопка «Подтвердить» →
   `graphService.approveCandidate` разворачивает `case_payload` в плоские
   поля и вызывает **тот же** `recordCase` с
   `author='agent:llm-extraction'`, `confidence` из кандидата,
   `documentId = source_document_id`. Кандидат получает `status='approved'`,
   `reviewed_at`. «Править» (PATCH) позволяет поправить поля перед
   подтверждением; «Отклонить» ставит `status='rejected'` (остаётся для
   аудита, в граф не идёт). Есть пакетные действия.

Логика создания случая **не дублируется** — переиспользуется
`recordCase` / `recordCaseTx` Этапа 1. Этап 3 добавил в них только
опциональные `author` / `confidence` с обратно совместимыми дефолтами
(`"user:manual"` / `1.0`).

## Дедупликация оборудования

Отдельная дедупликация в сервисе подтверждения **не реализована** — она
уже встроена в `recordCaseTx` через `findNodeByName('equipment', …)`
(поиск неархивного узла по имени, `ILIKE`). `approveCandidate` передаёт
`equipmentName` (а **не** `equipmentId`), поэтому при подтверждении случая
с уже существующим оборудованием новый узел не создаётся — случай
привязывается к существующему. Проверено интеграционным тестом
(два кандидата с одинаковым именем оборудования → один узел `equipment`).

## Факты не переписываются

Извлечение НЕ переписывает факты: серийные номера, теги, коды, адреса,
даты переносятся **дословно**. Это явно прописано в дефолтном промпте.
Нормализация только обрезает пробелы и приводит структуру к контракту;
содержимое текстовых полей не трогается.

## Graceful fallback

Извлечение никогда не ломает импорт/граф:

- провайдер выключен / не сконфигурирован / нет модели / пустой промпт →
  POST сразу возвращает `ok:false` с понятным русским сообщением, кнопка
  показывает его, ничего не создаётся;
- документ не текстовый (PDF/XLSX/CSV) или без текста → понятное
  сообщение, ничего не создаётся;
- ошибка/таймаут вызова модели на сегменте → сегмент пропускается; если
  упали все сегменты — задача завершается со статусом `error`
  (кандидаты не созданы);
- невалидный JSON ответа → сегмент пропускается (JSON-ремонт пытается
  починить заранее).

## Настройки (`app_settings.knowledge_extraction`)

Хранятся в БД, редактируются в UI (вкладка «Настройки → Поиск →
Извлечение знаний»), по образцу HyDE / обогащения:

| Поле | Дефолт | Границы | Описание |
|---|---|---|---|
| `enabled` | `false` | — | главный тумблер; срабатывает только по ручному запуску |
| `providerId` | `""` | — | облачный провайдер (текст документа уходит ему) |
| `model` | `""` | — | перебивает модель провайдера; пусто — модель провайдера |
| `maxTokens` | `2000` | 500..8000 | длина JSON-ответа со случаями |
| `timeoutMs` | `60000` | 5000..180000 | таймаут на один вызов модели |
| `prompt` | дефолт ниже | ≤16000 симв. | системный промпт извлечения |

У каждого поля настроек и у каждого действия на экране ревью — подсказка
«?»/хинт: что делает и когда срабатывает. Особо поясняется, что
извлечённое — черновики, требующие подтверждения, и в граф попадает
только после «Подтвердить».

### Дефолтный промпт (редактируется в UI)

> Промпт **доменно-агностичен** (не предполагает АСУ ТП), хранится в БД и
> редактируется в UI; кнопка «Сбросить промпт к универсальному»
> восстанавливает значение ниже дословно.

```text
Ты извлекаешь из текста производственные случаи опыта эксплуатации. Каждый случай — это связка: какое ОБОРУДОВАНИЕ фигурирует, ЧТО С НИМ ПРОИЗОШЛО (неисправность, отказ, событие) и ЧТО СДЕЛАЛИ (решение, действие).
Правила:
- Переноси точные обозначения, модели, серийные номера, теги, коды, адреса и даты ДОСЛОВНО, как в тексте. Ничего не исправляй, не дополняй и не выдумывай.
- Если какого-то поля в тексте нет — оставь его пустым (null). Не придумывай значения.
- Не объединяй разные случаи в один и не дроби один случай на несколько.
- Для каждого случая приведи source_quote — короткую дословную цитату из текста, на которой основан случай (для проверки человеком).
- Даты указывай в формате YYYY-MM-DD, только если они однозначно определяются из текста; иначе null.
- confidence — твоя оценка уверенности в случае от 0 до 1.
Извлекай случаи из любой предметной области (оборудование, приборы, узлы, машины, ПО — что угодно). Если в тексте нет ни одного случая — верни пустой список.
```

К этому промпту сервис добавляет жёсткое напоминание о формате ответа
(строгий JSON `{"cases":[…]}` без markdown, пустой список — если случаев
нет).

## Выбор модели

Для извлечения используйте **не-reasoning** модель. Reasoning-модели
(например, DeepSeek `deepseek-v4-pro` и подобные) тратят лимит токенов на
скрытое рассуждение → JSON-ответ обрывается на полуслове → парсер честно
возвращает 0 случаев (graceful fallback срабатывает, граф не загрязняется,
но результат пустой). Подробнее о механике расхода токенов на рассуждение —
см. `docs/CLOUD_PROVIDER.md`, раздел «Reasoning-токены расходуют общий
лимит».

**Рекомендованная рабочая связка** (проверена боевым smoke на `Вахта.docx`
— 10 корректных случаев, факты перенесены дословно):

- провайдер — **DeepSeek**;
- поле «Модель» в разделе извлечения — **`deepseek-v4-flash`** (не-reasoning);
- `maxTokens` — **≥ 4000** (на боевом прогоне ставили 8000).

**Важно: поле «Модель» заполняйте явно** не-reasoning моделью. Если оставить
его пустым, берётся **дефолтная модель провайдера** — а у DeepSeek по
умолчанию это reasoning-модель (`deepseek-v4-pro`), и тогда извлечение будет
стабильно возвращать 0 случаев. Это контринтуитивно: подсказка в UI говорит
«оставьте пустым — возьмётся модель провайдера», но для извлечения такой
дефолт почти всегда оказывается reasoning-моделью и рвёт ответ. Поэтому
оставлять поле пустым здесь не следует.

## REST API

См. `docs/API_SPEC.md` (раздел «Извлечение знаний / очередь кандидатов»).
Кратко:

- `POST /api/v2/graph/extract/:documentId` — запуск извлечения (async).
- `GET /api/v2/graph/extract/status/:jobId` — статус задачи.
- `GET /api/v2/graph/candidates` — список кандидатов (фильтры:
  `documentId` / `extractionJobId` / `status`).
- `GET /api/v2/graph/candidates/runs` — список запусков по документам.
- `PATCH /api/v2/graph/candidates/:id` — правка `case_payload`/`confidence`
  (только `pending`).
- `POST /api/v2/graph/candidates/:id/approve` — подтвердить (→ граф).
- `POST /api/v2/graph/candidates/:id/reject` — отклонить.
- `POST /api/v2/graph/candidates/approve` / `…/reject` — пакетно (`{ids:[]}`).

## Ограничения и риски

- **Стоимость LLM.** Извлечение — облачные вызовы (по сегментам для
  крупных документов). Запускается вручную, чтобы стоимость
  контролировалась пользователем.
- **Документы уходят в облако.** Текст документа отправляется выбранному
  облачному провайдеру. Учитывайте конфиденциальность.
- **Только текстовые документы.** `docx` / `txt` / `md`. Для PDF и XLSX
  кнопка скрыта: XLSX наполняет граф своим парсером, PDF — вне scope этой
  итерации.
- **Качество зависит от модели и промпта.** Поэтому всё проходит ручное
  ревью; в граф попадает только подтверждённое.
- **Симптом «извлечение даёт 0 кандидатов при работающем провайдере».**
  Почти всегда это reasoning-модель + малый лимит токенов: рассуждение
  съедает бюджет, JSON обрывается, парсер возвращает 0 случаев. Диагностика
  — смотреть `rawHead` / `rawLength` в `docker logs localrag-kb-api` (строка
  `"не удалось разобрать JSON ответа"`). Если `rawHead` оборван на середине
  строки — ответ обрезан по лимиту/reasoning: увеличьте `maxTokens` и/или
  смените модель на не-reasoning (см. раздел «Выбор модели»).
- **Одна дата на случай.** `recordCase` хранит одну дату случая: при
  переносе берётся `fault.date`, иначе `solution.date` (она проставляется
  в атрибуты и неисправности, и решения).
- **Статусы задач — in-memory.** Прогресс запуска хранится в памяти
  процесса (для опроса из UI). Сами кандидаты долговечны в Postgres; при
  перезапуске сервера теряется только транзиентный статус задачи —
  кандидаты остаются в очереди.
