# Project Context

## Что строим

Локальную систему поиска и консультаций по рабочим документам пользователя.
Это не “чат вообще обо всём”, а рабочий консультант по документации АСУ ТП:

- PDF
- таблицы
- теги и сигналы
- функциональные блоки
- схемы
- эксплуатационная документация

## Архитектурная идея

Архитектура должна быть правильной уже сейчас, даже если ноутбук слабый.
То есть:

- границы сервисов держим сразу
- перенос на другой ПК должен быть без переделки
- модели меняются через конфиг, а не через перестройку проекта

## Текущий стек

- `Open WebUI`
- `Ollama`
- `kb-api` на Fastify
- `PostgreSQL`
- `Qdrant`
- локальная файловая система для документов и артефактов

## Почему не делаем “тяжёлого универсального агента”

Потому что текущая задача уже имеет хороший узкий путь:

- импорт документа
- разбор текста
- поиск
- ответы с опорой на найденные фрагменты

На текущем железе именно такой путь даёт максимальную пользу.

## Реальный пользовательский сценарий

Пользователь должен уметь:

1. положить рабочие документы в `data/raw`
2. запустить импорт через браузер
3. видеть прогресс задач
4. при необходимости остановить или повторить задачу
5. очистить старые дубли индекса
6. искать по документам и страницам PDF
7. находить нужную страницу/раздел/тег
8. получать ответ по найденным источникам

Следующий слой сценария — разделы базы знаний. Они нужны, чтобы держать отдельно разные объекты, цеха, проекты или папки документации и затем ограничивать библиотеку, поиск и ответы выбранным разделом.

## Что важно для этой предметной области

Для АСУ ТП важны не только обычные абзацы, но и:

- страницы содержания
- листы изменений
- теги сигналов
- перечни I/O
- схемные страницы
- таблицы
- экраны и HMI-подобные листы

Из-за этого в проекте уже есть page-level слой для PDF и классификация страниц.

## Практические ограничения

- слабый ноутбук
- CPU-only инференс
- ограниченный диск `C:`

Из-за этого нужны специальные режимы работы:

- фоновый импорт
- прогресс задач
- пакетная индексация малыми порциями
- лёгкий режим PDF без preview

## Что уже подтверждено практикой

Самая тяжёлая проблема оказалась не в модели, а в диске:

- при заполнении `C:` падал Qdrant
- большой PDF доходил до первой партии и падал с `Internal Server Error`
- в логах была реальная причина: `No space left on device`

Это означает, что для стабильной эксплуатации нужно следить не только за RAM, но и за свободным местом.

## Что уже закрыто как первый рабочий этап

К `2026-04-25` базовый эксплуатационный слой уже считается рабочим:

- тяжёлый PDF `g2043_ru_04-1.pdf` успешно проиндексирован до `655 / 655`
- в системе есть основной браузерный режим `Консультант`
- дубли индексированных файлов можно найти и убрать через UI
- при отсутствии релевантных источников система должна честно вернуть пустой результат, а не выдумывать ответ

Это означает, что первая практическая цель "локальный консультант по рабочим PDF АСУ ТП" уже достигнута на базовом уровне.

К `2026-04-26` добавлен первый безопасный backend-слой разделов базы знаний:

- создана схема дерева `knowledge_nodes` + closure;
- создан системный раздел `Без раздела`;
- добавлен API `/nodes` для управления деревом;
- добавлен API привязки документов к разделам;
- добавлен ручной пересчёт Qdrant payload для разделов документа;
- добавлена автоматическая синхронизация Qdrant payload затронутых документов после rename/move/delete раздела;
- endpoints импорта принимают `nodeIds`/`primaryNodeId` и сразу пишут разделы в PostgreSQL + Qdrant payload;
- добавлена ручная синхронизация `POST /admin/reindex-nodes` и статус `GET /admin/sync-status`, чтобы старые документы тоже получили payload разделов перед включением scoped search;
- добавлен безопасный recovery-контур Qdrant: статус `GET /admin/qdrant-status`, фоновая пересборка `POST /admin/rebuild-qdrant` из PostgreSQL chunks/assets и скрипт переноса повреждённой коллекции в backup.
- `/search`, `/search/pages`, `/ask`, `/ask/pages` принимают `nodeId/includeChildren` и `selectedTags`, фильтруют semantic + lexical retrieval по выбранному разделу и тегам документа.
- `/ui/consult` получил выбор рабочего раздела, scoped-список документов и URL-состояние `nodeId/includeChildren`.
- `/ui/consult` показывает основной и дополнительные разделы в карточках документов; источники поиска показывают `node_paths`, если они есть в payload.
- `GET /tags` и окно `#` в `/ui/consult` работают в текущем scope раздела, чтобы теги не смешивались между разделами.
- `/ui/pages-search` получил выбор рабочего раздела, scoped-список документов и передачу `nodeId/includeChildren` в поиск/ответы по PDF-страницам.
- `/ui/jobs` получил выбор рабочего раздела, scoped-список задач и URL-состояние `nodeId/includeChildren`.
- `/ui/ingest` получил выбор primary-раздела и дополнительных разделов для нового импорта; upload/ingest-запросы передают полный `nodeIds` и `primaryNodeId`, а правая очередь и история фильтруются по выбранному рабочему разделу.
- `/ui/nodes` получил первую рабочую страницу управления деревом: просмотр счётчиков и документов выбранного раздела с прямыми привязками к разделам, создание пользовательских разделов, редактирование, перемещение, массовая привязка документов к выбранному разделу, отвязка выбранных документов от текущего пользовательского раздела, экспорт/импорт дерева, показ результата автоматической синхронизации payload и ручная синхронизация payload раздела. Удаление через UI доступно только для пустого пользовательского раздела после проверки счётчиков и ввода точного названия.

К `2026-04-28` спецификация `docs/knowledge-nodes-spec.md` закрыта как полный рабочий слой:

- системный раздел `Без раздела` принудительно работает без вложенного режима;
- `/nodes` отдаёт ETag/304 и использует backend cache строк дерева;
- `node_counters` обновляется SQL-триггерами;
- включена ручная и фоновая выборочная сверка payload разделов;
- `/ui/nodes` поддерживает drag-and-drop документов на разделы;
- `cascade_documents` реализован только через API с двойным подтверждением, UI остаётся безопасным;
- `POST /documents/:id/open-local` отдаёт helper-контракт для локального открытия файла;
- regression smoke закреплён в `scripts/knowledge-nodes-smoke.mjs`.

Также на `2026-04-28` добавлен первый лёгкий визуальный слой для PDF:

- классификатор страниц усилен до версии `v3` под содержания, таблицы, схемы, экраны, сигналы, клеммы и функциональные блоки;
- `POST /documents/:id/rebuild-visual-assets` точечно создаёт preview/OCR для выбранных страниц без повторного импорта всего PDF;
- OCR работает только локально через `tesseract`, если он установлен, и не использует внешние API;
- `POST /search/visual` и кнопка `Визуальный поиск` на `/ui/pages-search` ищут по визуальным page assets (`scheme`, `screen`, `table`, `signals`);
- `POST /admin/reset-content` и `scripts/reset-rag-content.ps1` очищают тестовое содержимое базы, сохраняя схему и системный раздел.

## Какой режим сейчас считается правильным

### Первый проход по большой папке

- фоновый импорт
- без preview страниц

### Второй проход по важным PDF

- точечная переиндексация
- с preview страниц

Так мы получаем сначала устойчивую текстовую базу, а потом уже постепенно добавляем визуальный слой.
