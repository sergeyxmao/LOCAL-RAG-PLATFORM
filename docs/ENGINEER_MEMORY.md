# Память инженера — Этап 1: ручная запись случаев

## Что делает

«Память инженера» — это универсальный слой графа знаний для
накопления **опыта эксплуатации**: какое оборудование, что с ним
произошло, что сделали. Работает для любой темы (АСУ ТП, электрика,
КИП), не привязан к таблицам сигналов и не требует загрузки
документов.

Раньше граф (`graph_nodes`/`graph_edges`) наполнялся только парсером
XLSX из таблиц сигналов АСУ ТП — узкий структурный слой, бесполезный
вне домена сигналов. Ручное наполнение смыслами было возможно только
через generic-CRUD, где на один случай нужно вручную создать
несколько узлов и связей по одному. Это непригодно для оперативной
записи.

Теперь инженер на странице `/ui/v2/graph` нажимает **«Записать
случай»**, за одну форму фиксирует: оборудование, что произошло, что
сделали, дату, опционально объект и документ. Один сабмит создаёт
нужные узлы и связи **атомарно** (в одной транзакции). Записанное
сразу видно в существующем дереве / поиске / карточке узла графа.

Этап 1 — это **ручная запись**. Дата случая хранится атрибутом узла
(вариант А), отдельный тип события не вводится. Тип `event` (события /
журнал) отложен.

> **Этап 3 (наполнение из документов).** Память инженера теперь
> наполняется не только вручную, но и **LLM-извлечением случаев из
> текстовых документов** (`docx`/`txt`/`md`) — кнопка «Извлечь знания» в
> Базе знаний. Извлечённое НЕ попадает в граф напрямую: оно складывается
> в очередь кандидатов (`graph_extraction_candidates`) и переносится в
> граф **только после подтверждения** пользователем на экране ревью
> («Граф знаний → Кандидаты»). Перенос идёт через тот же
> `recordCase`/`recordCaseTx`, но с `author='agent:llm-extraction'`.
> Подробно — `docs/KNOWLEDGE_EXTRACTION.md`.

## Расположение в коде

- Встроенные типы узлов: `apps/kb-api/src/services/graphNodeTypeService.js`
  (`BUILTIN_TYPES` + `ensureBuiltinTypes()`) — добавлены `equipment`,
  `fault`, `solution`.
- Композитный метод: `GraphService.recordCase(payload)` в
  `apps/kb-api/src/services/graphService.js` — валидация и нормализация
  входа, вызов транзакции, маппинг результата.
- Транзакция: `PostgresProvider.recordCaseTx(payload)` в
  `apps/kb-api/src/providers/postgresProvider.js` — `BEGIN` →
  поиск/создание узлов и связей через один клиент → `COMMIT`;
  при ошибке `ROLLBACK`.
- Роут: `POST /api/v2/graph/case` в `apps/kb-api/src/routes/graph.js`
  со `schema`-валидацией Fastify/AJV (`schema.body`, `schema.response`
  для 200/400/500). Ошибки — на русском.
- UI: кнопка «Записать случай» и модалка-форма в
  `apps/kb-api/src/routes/uiV2Graph.js`. Русификация связей — через
  словарь `EDGE_TYPE_LABELS` (`relates_to`/`resolves`/`located_at`).

## Как использовать

### Через UI

1. Открыть `/ui/v2/graph`.
2. Нажать **«📝 Записать случай»** (кнопка в подвале левой панели,
   рядом с «Создать узел»).
3. Заполнить форму:
   - **Оборудование** (обязательно) — автокомплит по существующим
     `equipment`-узлам; можно ввести новое имя (тогда узел создаётся).
   - **Модель / Место** (опционально) — уходят в `attributes.model` /
     `attributes.location` нового оборудования.
   - **Объект / площадка** (опционально) — автокомплит по
     `object`-узлам или новое имя.
   - **Что произошло** (обязательно) — суть неисправности.
   - **Что сделали** (опционально) — решение.
   - **Дата** — по умолчанию сегодня.
   - **Связанный документ** (опционально) — выбор из загруженных.
4. Сабмит → toast с итогом («Создано: оборудование / неисправность /
   решение») → дерево и счётчики обновляются, открывается карточка
   созданной неисправности.

### Через REST API

```bash
curl -X POST http://localhost:8787/api/v2/graph/case \
  -H "Content-Type: application/json" \
  -d '{
    "equipmentName": "Метран-150",
    "faultText": "дрейф нуля",
    "solutionText": "продувка импульсной линии",
    "objectName": "КНС-6 ЦППД-4",
    "date": "2026-05-29"
  }'
```

Ответ:

```json
{
  "ok": true,
  "nodes": {
    "equipment": { "id": "...", "type": "equipment", "name": "Метран-150", ... },
    "object":    { "id": "...", "type": "object",    "name": "КНС-6 ЦППД-4", ... },
    "fault":     { "id": "...", "type": "fault",     "name": "дрейф нуля", ... },
    "solution":  { "id": "...", "type": "solution",  "name": "продувка импульсной линии", ... }
  },
  "edges": [ ... ],
  "created": { "equipment": true, "object": true, "fault": true, "solution": true }
}
```

Поля тела запроса:

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `equipmentId` | UUID, nullable | — | Использовать существующее оборудование по id |
| `equipmentName` | string, nullable | обяз., если нет `equipmentId` | Имя оборудования (поиск ILIKE / создание) |
| `equipmentModel` | string, nullable | — | `attributes.model` нового оборудования |
| `equipmentLocation` | string, nullable | — | `attributes.location` нового оборудования |
| `objectId` | UUID, nullable | — | Использовать существующий объект по id |
| `objectName` | string, nullable | — | Имя объекта (поиск ILIKE / создание) |
| `faultText` | string | **да** | Что произошло (полный текст) |
| `solutionText` | string, nullable | — | Что сделали |
| `date` | string (YYYY-MM-DD), nullable | — | Дата случая → `attributes.date` |
| `documentId` | UUID, nullable | — | Связанный документ → `source_document_id` |

`created.*` — флаги, был ли узел создан заново (`true`) или найден
существующий / не создавался (`false`). `fault` всегда `true`.

## Технические детали

### Типы узлов

- `equipment` (🔧 «Оборудование») — зонтичный тип: датчик, насос,
  кабель, автомат, клеммник. **Не путать** с `device` (узкий полевой
  прибор слоя сигналов АСУ ТП).
- `fault` (⚠️ «Неисправность») — `name` = краткая суть (первые ~80
  символов текста, схлопнутые пробелы), `description` = полный текст,
  `attributes.date` = дата.
- `solution` (✅ «Решение») — создаётся только если заполнено «Что
  сделали»; `name` / `description` / `attributes.date` — аналогично.

Все три помечены `is_builtin = TRUE` (идемпотентный
`INSERT ... ON CONFLICT (code) DO UPDATE SET is_builtin = TRUE`),
их `code` неизменяем, удалить нельзя.

### Связи

- `relates_to` — `fault` → `equipment` («относится к»);
- `resolves` — `solution` → `fault` («устраняет»);
- `located_at` — `equipment` → `object` («находится на»).

Это свободные `relation` (поле TEXT, не enum). Русификация — только
в UI через `EDGE_TYPE_LABELS`. Связи создаются через существующий
механизм с `ON CONFLICT (source_node_id, target_node_id, relation)
DO NOTHING` — повторная запись того же триплета не плодит дубли.

### Связь с документом

Связь с документом **не** делается ребром: `graph_edges.target_node_id`
ссылается только на `graph_nodes`, а документ живёт в таблице
`documents`. Поэтому «связанный документ» проставляется через поле
`source_document_id` у создаваемых узлов — там же штатно отрабатывает
удаление документа по FK.

### Атомарность

Вся запись случая выполняется в одной транзакции
(`PostgresProvider.recordCaseTx`): один клиент пула, `BEGIN`,
последовательные `INSERT`/`SELECT`, `COMMIT`. При любой ошибке —
`ROLLBACK` целиком и ответ `500` с русским сообщением, лог через
`request.log.error`. Частично записанных случаев не бывает.

### Автор и уверенность (`author` / `confidence`)

С Этапа 3 `recordCase` и `recordCaseTx` принимают опциональные `author`
и `confidence` (обратно совместимо — при отсутствии полей сохраняется
поведение Этапа 1: `author='user:manual'`, `confidence=1.0`). Ручная
форма по-прежнему создаёт узлы с `user:manual` / `1.0`; подтверждение
кандидата LLM-извлечения передаёт `author='agent:llm-extraction'` и
`confidence` из кандидата. Колонки `author`/`confidence` уже были в
`graph_nodes`/`graph_edges` — это изменение кода, не схемы.

### Слой памяти параллельно RAG и графу сигналов

Память инженера — это **третий, параллельный слой** знаний:

- RAG (Qdrant + чанки) — полнотекстовый retrieval по документам;
- граф сигналов (парсер XLSX) — структурный слой АСУ ТП;
- память инженера (ручная запись) — накопление опыта эксплуатации.

Запись случая — это несколько SQL `INSERT`, **без эмбеддингов и без
обращений к Ollama**. Рабочие RAG-коллекции Qdrant не затрагиваются.

## Ограничения и риски

- **Новые типы плоско в дереве.** `HIERARCHY_RULES` (правила дерева)
  про `equipment`/`fault`/`solution` не знают — узлы показываются
  плоскими группами «Оборудование» / «Неисправность» / «Решение»,
  без вложенности. Иерархия памяти — отдельная будущая задача.
- **Память наполняется вручную и LLM-извлечением (Этап 3).** Ручная
  форма «Записать случай» + кнопка «Извлечь знания» у текстовых
  документов. Извлечённое проходит через очередь кандидатов и ручное
  подтверждение — автоматической записи в граф из документов нет.
- **Тип `event` не введён.** Дата хранится атрибутом; журнал
  событий отложен.
- **Поиск оборудования по имени — ILIKE.** Совпадение по точному
  имени (без нормализации синонимов). Если ввести имя с другим
  написанием — создастся новое оборудование. Дедупликация написаний
  — будущая задача.
- **Нагрузка near-zero.** Несколько `INSERT` в транзакции, без
  тяжёлых операций.
