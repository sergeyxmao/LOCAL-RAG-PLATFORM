# Граф знаний в answer-pipeline (#8.3)

Подключение графа знаний (`graph_nodes` / `graph_edges`) к ответам ассистента
как источника истины для **структурных** вопросов.

## Что делает

Граф знаний наполняется из трёх источников (XLSX-парсер, ручные случаи,
LLM-извлечение) и виден в UI `/ui/v2/graph`. До #8.3 answer-pipeline о нём не
знал: структурные вопросы с идентификатором («какой адрес у сигнала
`KS_T2B1`», «что в шкафу `IO-03`», «где плата `DII8P24`») шли только в RAG
(Qdrant + чанки) и возвращали похожий текст вместо точного факта.

Теперь при вопросе, содержащем **идентификатор-подобный термин** (с цифрой
или дефисом), pipeline дополнительно ищет совпадение в графе. Если найден узел
с матчем по имени или ключевому структурному атрибуту — узел и его прямые
связи подмешиваются в промпт отдельным блоком `{graph_facts}` и попадают в
`sources` ответа с пометкой `origin:"graph"`. Если RAG пуст, но граф дал
факт — система отвечает по графу (`mode:"graph-only"`), а не `fallback-empty`.

Закрываемые сценарии: «адрес сигнала по тегу», «состав шкафа», «где
установлена плата».

## Как использовать

### Через UI чата (`/ui/v2/chat`)

Задайте структурный вопрос с тегом/адресом/идентификатором, который есть в
графе, например:

```
какой адрес у сигнала KS_T2B1
```

В ответе появится точный факт из графа; под ответом — бейдж `граф: N фактов`;
в источниках — карточка с пометкой `🕸 граф` и ссылкой в раздел графа.

Обычный смысловой вопрос без идентификатора («как обслуживать манометр») граф
**не** трогает — бейджа нет, поведение как раньше.

### Через API

```bash
# Структурный вопрос с тегом из графа
curl -X POST http://localhost:8787/ask \
  -H "Content-Type: application/json" \
  -d '{"question":"какой адрес у сигнала KS_T2B1"}'
# → в JSON: sources с "origin":"graph", "resource_type":"graph_node",
#   "graph": { "used": true, "count": N }, mode не "fallback-empty".

# Обычный вопрос без идентификатора
curl -X POST http://localhost:8787/ask \
  -H "Content-Type: application/json" \
  -d '{"question":"как обслуживать манометр"}'
# → графовых источников нет, "graph": { "used": false, ... }, mode "llm".
```

В чате `/ui/v2/chat` (стрим и нестрим, local и cloud) — то же поведение, плюс
бейдж и карточки.

## Технические детали

### Триггер релевантности графа

В `graphAnswerService.lookup(query, { limit })`:

1. Выделяются идентификатор-подобные термины тем же правилом, что в
   `SearchService.identifierTerms()` — **термин содержит цифру или дефис**
   (правило продублировано с комментарием-ссылкой, чтобы не тянуть весь
   `SearchService`).
2. Идентификаторов нет → `{ used:false, reason:"no_identifier", facts:[] }`.
   Граф не трогаем — RAG-only вопросы графом не зашумляются.
3. Есть → по **каждому очищенному** идентификатор-термину вызывается
   `graphSearchService.search(term, { limit: 5 })`, матчи объединяются
   (дедуп по `node.id`), приоритизируются по типу узла и обрезаются до
   `MAX_NODES = 6` (см. «Приоритет типов узлов и лимит» ниже).

   Термины очищаются от пунктуации правилом, близким к
   `searchService.normalizeQueryTerms()` (split по `[^a-z0-9а-яё_-]+`): из
   «TT-133?» получается `tt-133`. В `search()` уходит **чистый идентификатор**,
   а не сырой запрос с прилипшим знаком препинания — иначе `ILIKE %TT-133?%`
   не совпадал бы с именем узла «Датчик температуры TT-133». В отличие от
   `searchService`, графовый экстрактор дополнительно (а) распознаёт составные
   адреса целиком (см. ниже) и (б) сохраняет подчёркивание в классе символов.

#### Составные адреса не дробятся (#8.3.4)

Адрес вида `3:0:0:3` (или с точками `2.0.4.6`) — это **один** идентификатор,
а не четыре. Двоеточие и точка не входят в класс `[a-z0-9а-яё_-]`, поэтому
общий split дробил бы адрес на одиночные цифры `3`,`0`,`0`,`3`, и в
graph-search уходили бы осколки, цепляющие случайные узлы из **чужих** адресов
(соседние карты `3:0:0:2`, `3:0:1:0` и т.п.) вместо точного матча по полю
`address`.

Поэтому `extractIdentifierTerms()` сначала вытаскивает составные адреса
регуляркой `\d+(?:[:.]\d+)+` (2+ числовых групп через `:` или `.`) и сохраняет
их **целиком**, затем из остатка строки извлекает обычные термины прежним
правилом split; результаты объединяются с дедупом (адреса — первыми, как самые
специфичные). Так вопрос «Что подключено на адресе `3:0:0:3`?» даёт **один**
поиск по полному адресу — `graphSearchService.search("3:0:0:3")` находит сигнал
с `matchedField:"address"`, а приоритет типов поднимает его первым фактом.

Подчёркивание добавлено в класс split (`[^a-z0-9а-яё_-]+`), чтобы составные
теги вроде `K1_APK100` / `K1_DP5PP103` не дробились на `k1` + хвост.

### Допустимые `matchedField`

Принимаются только матчи по точным структурным полям:

```
name, tag, loop_tag, signal_address, address, cabinet_id
```

Прочие attribute-матчи (описания, комментарии) игнорируются как шумные. Если
принятых матчей нет → `{ used:false, reason:"no_match", facts:[] }`.

### Приоритет типов узлов и лимит (#8.3 — фикс потери сигналов)

`graphSearchService` отдаёт матчи в порядке приоритета **поля**: `name` →
`type` → `attributes`. Для адресного вопроса («что подключено на адресе
`3:0:0:3`») это давало баг: плата (`card`) и канал (`channel`) матчатся по
`name` и идут впереди, а сигнал (`signal`) матчится по `address`-атрибуту и
идёт **последним**. Жёсткий лимит резал список до приоритизации, и самый
ценный узел — «что физически подключено» — терялся.

Исправление в `lookup()`:

1. **Сбор с запасом.** Матчи накапливаются по всем идентификатор-терминам до
   `MAX_NODES * 4` кандидатов (ранний `break` по `MAX_NODES` убран), чтобы
   сигнал из «хвоста» выдачи успел попасть в пул **до** обрезки.
2. **Приоритизация по типу узла перед лимитом.** Принятые матчи стабильно
   сортируются по ценности типа для структурных вопросов
   (`NODE_TYPE_PRIORITY`, от высшего):

   ```
   signal, device, card, channel, station, cabinet, object, … (прочие в хвост)
   ```

   `signal`/`device` («что подключено») важнее носителя (`card`/`channel`) и
   места (`station`/`cabinet`/`object`). Сортировка стабильна — внутри одного
   типа сохраняется исходный порядок выдачи graph-search.
3. **Обрезка до `MAX_NODES = 6`** (было 3). Один адрес даёт кластер
   `card`+`channel`+`signal` (3 узла), а запрос может содержать несколько
   идентификаторов; 6 покрывают полный кластер одного адреса с запасом, не
   раздувая промпт (узлы компактны, связи лимитированы
   `MAX_RELATIONS_PER_NODE`). `DEFAULT_SEARCH_LIMIT` на узел остаётся 5.

Итог: при адресном вопросе граф отдаёт полный кластер адреса (плата + канал +
сигнал), **приоритет — сигналу/прибору**, и сигнал больше не вытесняется
картами/каналами того же адреса. Одиночный матч по имени (например, адрес
сигнала по тегу `FA-IO-03-A`) работает как раньше. Дедуп по `node.id`
сохранён (`seen`).

### Обогащение связями (+1 уровень)

Для каждого принятого узла (**максимум 6 узлов**) вызывается
`graphService.getRelatedNodes(node.id, { direction:"both" })`. Связи
ограничены **8 на узел**. Русификация `relation` берётся из словаря
(зеркало `EDGE_TYPE_LABELS` из `routes/uiV2Graph.js`); неизвестные связи
показываются сырым кодом.

### Формат на выходе сервиса

```js
{
  used: true,
  reason: "ok",
  count: N,
  facts: [
    {
      nodeId, type, name,
      attributes,                 // ключевые атрибуты узла
      relations: [                // до 8 связей
        { relation, rawRelation, direction, targetType, targetName }
      ],
      matchedField,
      origin: "graph"
    }
  ]
}
```

### Блок `{graph_facts}` в промпте

Графовые факты идут **отдельным блоком**, НЕ в RRF-фьюжне (у узлов нет
vector/lexical-скоров). Подставляются через плейсхолдер `{graph_facts}` в
системном промпте. В `DEFAULT_SYSTEM_PROMPT` есть секция «Структурные факты из
графа знаний» с инструкцией: при наличии точного факта в графе — приоритет
факту над текстом источников.

#### Защита от потери факта при кастомном шаблоне

`renderSystemPrompt()` гарантирует, что графовый факт дойдёт до модели
**независимо** от того, есть ли в шаблоне плейсхолдер `{graph_facts}`:

- **Плейсхолдер есть** — блок подставляется на его место (как обычно).
- **Плейсхолдера нет, но факты есть** — блок **принудительно дописывается в
  конец** системного сообщения отдельной секцией с заголовком
  `=== СТРУКТУРНЫЕ ФАКТЫ ИЗ ГРАФА ЗНАНИЙ ===` и краткой инструкцией приоритета.
  Сам сохранённый пользовательский шаблон **не модифицируется** — дописывание
  происходит только в рантайме при сборке сообщения.
- **Фактов нет** — ничего не добавляется (поведение без изменений).

Это закрывает типичный боевой случай: у пользователя свой рабочий промпт без
`{graph_facts}`, граф нашёл факт (карточка 🕸 и бейдж видны), но раньше факт не
попадал в текст промпта — модель отвечала «источников нет» и фантазировала.
Теперь факт всегда в системном сообщении. В UI настроек промпта показывается
информационное предупреждение, если плейсхолдер не вписан (с подсказкой, что
факт будет дописан автоматически).

> Примечание: нестрим local-путь через `answerService` собирает промпт инлайн
> (без шаблонов) и **всегда** включает графовый блок — там потеря факта была
> невозможна и до этого фикса.

В `sources` графовые записи добавляются **после** RAG-источников
(`origin:"graph"`, `resource_type:"graph_node"`) со своей нумерацией, чтобы
ссылки `[N]` на RAG-источники оставались консистентными.

### Пустой RAG → `graph-only`

Если `hybrid.items` пуст, НО `graphAnswer.used === true`:

- НЕ возвращается `fallback-empty`;
- промпт собирается с `{graph_facts}` (sources-блок = «Источники не найдены»);
- генерируется ответ LLM;
- `mode` помечается как `"graph-only"`.

Если и граф пуст, и RAG пуст → прежний `fallback-empty` без изменений.

### Метаданные ответа

В `metadata` сообщения добавляется `graph: { used, count, reason }` (по
образцу `hyde` / `reranking`) — источник для UI-бейджа.

## Ограничения и риски

- **Разнописания оборудования** — известное ограничение. «ИБП Smart UPS RT
  1000 SURT1000XL» и «Smart UPS RT 1000» создают **разные** узлы, поэтому
  факт может не найтись по другому написанию. Дедупликация узлов —
  отдельная будущая задача (пункт A слоя памяти), **вне рамок #8.3**.
- **Нагрузка**. Graph-lookup — это `ILIKE` по Postgres + до `MAX_NODES` (6)
  запросов связей, **без LLM-вызовов**. Дополнительной классификации «структурности» вопроса
  LLM-ом нет — триггер чисто эвристический (наличие идентификатора).
- **Недоступность Postgres**. Graph-lookup ловит ошибку и возвращает
  `used:false` (`reason:"error"`, `warn` в логах) — RAG-ответ при этом
  **не падает**.
- **Кастомный системный промпт без `{graph_facts}`**. У пользователей,
  сохранивших свой шаблон без плейсхолдера, факты графа в промпт не попадут,
  но останутся в `sources` и `metadata`. В UI настроек промпта показывается
  мягкое предупреждение.
- **Совместимость**. Qdrant payload и логика chunking не меняются —
  переиндексация не требуется. При пустом графе поведение pipeline идентично
  текущему.

## История изменений

- 2026-06-02 — #8.3.4: `extractIdentifierTerms()` больше не дробит составной
  адрес. Раньше split по `[^a-z0-9а-яё-]+` разбивал `3:0:0:3` на четыре
  одиночные цифры (`identifiers:4`), graph-search искал по осколкам `3`/`0` и
  цеплял случайные узлы из чужих адресов, а реальный сигнал `K1_DP5PP103` на
  `3:0:0:3` терялся. Теперь составные адреса (`\d+(?:[:.]\d+)+`, форматы с `:`
  и `.`) распознаются регуляркой ДО общего split и уходят в `search()`
  целиком; в класс split добавлено подчёркивание, чтобы теги `K1_APK100` /
  `K1_DP5PP103` не дробились. Приоритет типов и `MAX_NODES=6` из #8.3.3 не
  тронуты — теперь они получают корректный вход. Правка только в
  `extractIdentifierTerms()`; БД, Qdrant, граф-схема не затронуты.
- 2026-06-01 — #8.3.3: фикс потери сигналов при адресном lookup. Раньше
  graph-search отдавал матчи в порядке приоритета поля (`name` → `type` →
  `attributes`), и при адресном вопросе («что подключено на адресе `3:0:0:3`»)
  плата/канал (матч по `name`) шли впереди сигнала (матч по `address`), а
  жёсткий лимит `MAX_NODES = 3` резал список **до** приоритизации — самый
  ценный узел (сигнал, «что подключено») терялся. Теперь `lookup()` собирает
  кандидатов с запасом (`MAX_NODES * 4`, ранний `break` убран), **стабильно

  card/channel выше места) и только затем обрезает до `MAX_NODES = 6` (поднят
  с 3 — покрывает полный кластер одного адреса card+channel+signal с запасом).
  Адресный вопрос теперь отдаёт сигнал первым; одиночный матч по имени сигнала
  (`FA-IO-03-A`) поведения не меняет. Правка чисто в `graphAnswerService` —
  БД, Qdrant, chunking и граф-схема не затронуты.
- 2026-05-31 — #8.3-followup: защита графовых фактов от потери при кастомном
  промпте. Если в шаблоне нет `{graph_facts}`, но факты есть —
  `renderSystemPrompt()` дописывает графовый блок в конец системного сообщения
  (рантайм, сам шаблон не меняется). В UI настроек промпта добавлен
  плейсхолдер `{graph_facts}` в подсказку и информационное предупреждение об
  авто-дописывании. Раньше при кастомном промпте факт молча терялся (был в
  `sources`/`metadata`, но не в тексте промпта).
- 2026-05-31 — #8.3-fix: идентификатор-термины очищаются от пунктуации перед
  graph-search. `lookup()` ищет по каждому **очищенному** термину (правило
  `normalizeQueryTerms`), а не по сырому запросу. Вопросы вида «…TT-133?»,
