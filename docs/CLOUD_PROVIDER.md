# Облачный ИИ (OpenAI-совместимый провайдер)

## Что делает

Позволяет подключить любой OpenAI-совместимый API (DeepSeek, OpenRouter, Groq,
Together, Mistral, локальный LM Studio и т.д.) и использовать его для генерации
ответов в чате вместо локальной Ollama. Эмбеддинги всегда остаются локальными —
облако используется только для генерации текста ответа.

Включается в `/ui/v2/settings` и активируется по выбору в чате: dropdown
**⚡ <имя провайдера> ▾ / 🔒 Локально** в шапке страницы `/ui/v2/chat`. Выбор
сохраняется на уровне сессии (`chat_sessions.provider`).

С полировки #4 можно добавить **несколько** облачных провайдеров одновременно
(DeepSeek, OpenRouter, Groq и т.п.) и переключаться между ними прямо в чате
без захода в Настройки. Активный провайдер сессии — `local` или
`cloud:<uuid провайдера>` в БД.

## Что попадает во внешний API при использовании

- Системный промпт (текст инструкции для модели).
- Последние 6 сообщений из истории чата (`role: 'user'` и `role: 'assistant'`).
- Текущий вопрос пользователя.
- Содержимое найденных чанков (фрагменты документов), которые отобрал
  локальный retrieval. По умолчанию — до 6 чанков, каждый обрезается до
  1200 символов.

## Что НЕ попадает во внешний API

- Эмбеддинги. Они всегда строятся локальной моделью `qwen3-embedding:0.6b`.
- Полные документы. Только фрагменты, которые попали в выборку retrieval.
- Метаданные документов (если они не процитированы в выбранных чанках).
- Логи и статистика kb-api.
- Другие сессии чата, к которым этот запрос не относится.

## Reasoning-модели (DeepSeek-V4, OpenAI o1 и т.п.)

С полировки итерации 3 тест подключения (кнопка «Проверить подключение») и
основной чат корректно работают с моделями, у которых включён thinking-режим:

- В тестовом запросе `max_tokens=50` (вместо прежних 10) — этого хватает
  reasoning-модели, чтобы успеть выдать «ОК» после внутреннего размышления.
- Если контент пустой, но `finish_reason === 'length'` или в ответе есть
  `reasoning_content` (DeepSeek), `reasoning` (OpenAI o1) или непустой
  `tool_calls` — мы трактуем это как «модель работает, соединение есть»
  (`thinkingMode = "reasoning"` или `"length-cutoff"`) и возвращаем
  `ok: true` с пояснением вместо `server_error: пустой ответ`.
- В стримящихся ответах (`generateStream`) `delta.reasoning_content` тоже
  учитывается — но в финальной плашке UI показывает только видимый текст
  (`delta.content`), как и должна.

### Reasoning-токены расходуют общий лимит

**Важно для пользователя.** У reasoning-моделей (DeepSeek `deepseek-v4-pro`,
OpenAI o1 и т.п.) скрытое рассуждение тратит токены **из того же лимита**,
который ограничивает длину ответа. Если лимит маленький (например, 1024),
а вопрос сложный — рассуждение съест весь бюджет, и на видимый ответ
не останется ни одного токена. Признаки этой ситуации в ответе провайдера:

- `finish_reason: "length"`;
- `reasoning_tokens` ≈ `max_tokens`;
- `content` пустой.

Симптом со стороны пользователя — «модель ничего не ответила». Чтобы этого
избежать, по умолчанию лимит поднят до **4096** и сделан настраиваемым (см.
ниже). Не-reasoning модели (`deepseek-v4-flash`) обычно укладываются и в
меньший лимит, поэтому проблема проявлялась преимущественно на pro.

Тот же эффект бьёт по **извлечению знаний из документов**: на reasoning-модели
JSON-ответ со случаями обрывается, и извлечение возвращает 0 кандидатов. Для
извлечения рекомендуется не-reasoning модель — см. `docs/KNOWLEDGE_EXTRACTION.md`,
раздел «Выбор модели».

Если лимит всё же исчерпан рассуждением, ассистент больше не отвечает
пустотой — вместо этого подставляется явное сообщение:

> Модель израсходовала весь лимит токенов на рассуждение (`<N>`) и не успела
> сформировать ответ. Увеличьте «Максимальную длину ответа» в настройках
> или упростите вопрос.

В `chat_messages.metadata` такая запись помечается `mode: "empty-reasoning"`,
с полями `finishReason`, `thinkingMode`, `maxTokensUsed` — пригодно для
отладки в логах БД.

## Максимальная длина ответа

Максимальное число токенов, которое модель может потратить на ответ,
настраивается в UI и применяется ко всем облачным запросам (стрим и обычный
`generate`). По умолчанию — **4096**, диапазон — **256–8192**.

- **Где настраивается:** `/ui/v2/settings` → вкладка «Модели и облако» →
  карточка «Длина ответа модели» → поле «Максимальная длина ответа модели
  (токенов)» → «Сохранить».
- **API:**
  - `GET /api/v2/settings/generation` → `{ ok: true, generation: { maxTokens } }`.
  - `PATCH /api/v2/settings/generation` с телом `{ "maxTokens": <int> }`.
    При значении вне диапазона 256..8192 — `HTTP 400` с русским сообщением
    об ошибке.
- **Хранение:** ключ `generation` в таблице `app_settings`
  (JSONB-структура `{ "maxTokens": 4096 }`). DDL не требуется — таблица
  key/value уже существует. См. `docs/DATA_SCHEMA.md`.
- **Применение:** `chatSessionService.resolveCloudMaxTokens()` читает
  значение и подставляет в `cloudChatProvider.generate` /
  `generateStream`. Локальная Ollama-генерация этим параметром не
  затрагивается.

Подсказки по выбору значения:

- `deepseek-v4-flash` и подобные не-reasoning модели — обычно достаточно
  1024–2048; на дефолте 4096 работают с запасом.
- `deepseek-v4-pro` и другие reasoning-модели — рекомендуется **4096 и
  выше**; при сложных многошаговых вопросах разумно поднять до 6000–8000.
- Больше лимит → дольше ответ и больше расход токенов облака; меньше → выше
  риск пустого ответа из-за исчерпания бюджета на reasoning.

## Как настроить

1. Открыть `http://localhost:8787/ui/v2/settings`.
2. В блоке «Облачные провайдеры» нажать **«+ Добавить провайдера»** и
   заполнить:
   - **Название провайдера** — свободный текст, например `DeepSeek`.
   - **Base URL** — корень API, например `https://api.deepseek.com`.
     Допустимо указывать без `/v1` — он будет добавлен автоматически.
     Если ваш провайдер требует другой путь (`/v2/chat/completions` и т.п.),
     укажите его в Base URL целиком — клиент уважает указанный путь.
   - **API Key** — ключ доступа, передаётся как `Authorization: Bearer ...`.
   - **Модель** — имя модели у провайдера, например `deepseek-chat`.
3. Нажать «Добавить» — карточка появится в списке. Первый добавленный
   провайдер автоматически становится **по умолчанию**.
4. Кнопка **«Тест подключения»** на карточке проверит реальный вызов
   `chat/completions` и покажет короткий ответ модели.
5. В чате в шапке появится dropdown **⚡ <имя> ▾** — рядом с пунктом
   «Локально (Ollama)». Кликом можно мгновенно переключиться на любого из
   настроенных провайдеров для текущей сессии.

### Несколько провайдеров

- Все провайдеры хранятся в `app_settings.cloudProviders` как массив
  `{ providers: [{id, name, baseUrl, apiKey, model}], defaultProviderId }`.
- При удалении провайдера по умолчанию приходит **HTTP 409** —
  сначала нужно нажать «Сделать по умолчанию» у другой карточки, потом
  удалять. Единственный провайдер удаляется без 409 — `defaultProviderId`
  обнуляется.
- В сессии чата хранится `cloud:<uuid провайдера>`. Если этот провайдер
  потом удалён, сессия автоматически использует
  `defaultProviderId` (если он есть) с пометкой в `metadata.providerFallback`.
  Если default'а тоже нет — ассистент отвечает «Облако не настроено».
- Старое значение `provider='cloud'` (до полировки #4) интерпретируется
  как «использовать default-провайдер» — сессии до миграции продолжают
  работать.

## Безопасность ключа

- Ключи хранятся в БД (`app_settings.cloudProviders.providers[*].apiKey`) в
  plaintext. Старый ключ `app_settings.cloudProvider` остаётся для совместимости
  и содержит дубликат на случай отката.
- Проект предполагается полностью локальным, без внешнего доступа к Postgres.
  Если БД будет открыта в сеть — ключ может утечь. Этот трейд-офф выбран
  осознанно вместо шифрования с master-key, который сам пришлось бы где-то
  хранить.
- В API ключ возвращается замаскированным (`sk-•••••a3f9`). Полный ключ
  никогда не отдаётся клиенту повторно после сохранения.
- При повторном сохранении: если в поле API Key осталась маска или пусто —
  старый ключ в БД сохраняется. Если ввели новый — записывается.
- В логи kb-api ключ не пишется ни в одной форме (ни в headers, ни в body
  запросов, ни в ошибках).
- **Только ASCII** в API-ключе (#8.1.c.fix-2). HTTP-заголовки по RFC 7230
  принимают только видимые US-ASCII (0x20–0x7E). При сохранении ключа
  `cloudChatProvider.prepareAuthorizationHeader()` тихо вычищает
  zero-width / control / BOM / биди-маркеры (часто пролезают при копи-пасте
  из браузера/PDF). Если после очистки остался не-ASCII символ
  (например, русская «С» U+0421 = 1057, которую путают с латинской «C») —
  возвращается понятная ошибка с **позицией** и **кодом** символа:
  «API-ключ содержит недопустимый символ на позиции 21 (код U+0421)…».
  Это лечит баг, когда GPT/Gemini падали с
  `Cannot convert argument to a ByteString…`, а DeepSeek работал
  (просто потому что ключи короче и реже задеваются мусором).
- В git не коммитится: БД не лежит в репозитории.

## Поведение при ошибках

- Нет интернета, 401 (неверный ключ), 403, 429 (rate limit), 5xx (ошибка
  сервера), timeout — ассистент отвечает текстом ошибки на русском и
  показывает кнопку **«Переключиться на локальный ИИ»**.
- Автоматический fallback на локальную модель отключён намеренно: пользователь
  сам решает, отправлять ли следующий запрос на локальную модель или
  переформулировать вопрос для облака.
- При ошибке `no_credentials` кнопка переключения не показывается — нужно
  настроить облако в «Настройках».

Классификация ошибок (`CloudProviderError.code`):

| код             | что значит                                          |
| --------------- | --------------------------------------------------- |
| `no_credentials`| Не задан Base URL, ключ или модель                  |
| `unauthorized`  | 401 или 403 — ключ неверный или просрочен           |
| `rate_limit`    | 429 — провайдер ограничивает запросы                |
| `server_error`  | 4xx (кроме 401/403/429) или 5xx — ошибка провайдера |
| `timeout`       | Превышен таймаут (по умолчанию 180 с — `CLOUD_CHAT_TIMEOUT_MS`, 25 с в тесте подключения) |
| `network`       | DNS, ECONNREFUSED, ENOTFOUND и т.п.                 |

## Таймаут облачных чат-запросов

Дефолт — **180 секунд** (`CLOUD_CHAT_TIMEOUT_MS=180000`), задаётся в `infra/.env.example` и пробрасывается в контейнер через `infra/docker-compose.yml`. Раньше был зашит в коде как 60 секунд — этого не хватало reasoning/pro-моделям с длинными ответами, и текст обрывался посреди абзаца.

Когда менять:
- **Поднять (300+ сек)**: используете тяжёлые reasoning-модели (DeepSeek-pro, o1, Claude Sonnet 4.6 thinking) на длинных запросах с большим контекстом.
- **Снизить (60 сек)**: используете только flash/turbo-модели, хотите быстрее ловить зависания.

Для тестов подключения в UI «Настройки → Облачные провайдеры → Тест» используется отдельный жёсткий таймаут 25 секунд — он не зависит от env, потому что тест должен быстро падать при битом ключе.

## Ограничения

- Эмбеддинги облачного провайдера игнорируются — в проекте всегда используется
  локальный `qwen3-embedding:0.6b`.
- История чата при отправке в облако обрезается до последних 6 сообщений +
  текущий вопрос (для экономии токенов и приватности). Локальная генерация
  работает без такой обрезки.
- Streaming поддерживается (`generateStream`) — клиент чата подписывается на
  SSE-эндпоинт `POST /api/v2/chat/sessions/:id/messages/stream`. Обычный
  `POST /messages` остался для обратной совместимости.
- Контроль над тем, что попадёт в облако, лежит на пользователе: фильтры в
  чате (раздел / документы) позволяют сузить поиск только до открытых
  документов, прежде чем отправить вопрос в облако.
